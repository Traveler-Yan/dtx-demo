# 第 1 章 从一个转账失败说起

## 1.1 本地事务的边界在哪里

Spring 的 `@Transactional` 绑定的是一份数据库连接。只要一次业务操作只落在一个库、一份连接上，
ACID 由数据库保证，开发者几乎不需要思考一致性。

```java
@Transactional
public void transfer(Long from, Long to, BigDecimal amount) {
    accountMapper.debit(from, amount);
    accountMapper.credit(to, amount);
}
```

这段代码之所以安全，是因为 `debit` 与 `credit` 共用同一个 `Connection`，`commit` 和 `rollback`
由同一个事务管理器发出。

一旦下面任意一条成立，这份保证就消失了：

- 一次操作要写多个库（分库分表、读写分离后的多写、业务库 + 日志库）
- 跨服务调用（订单服务扣库存、账户服务扣款）
- 跨中间件（写数据库 + 发 MQ + 更新 Redis）
- 跨系统（本系统下单、第三方支付扣款）

这时没有任何一个数据库能为"整体"回滚，于是需要分布式事务。

## 1.2 四个真实的失效场景

**场景一：跨库转账。** 订单库扣了款，账户库写失败，用户钱少了但订单没生成。

**场景二：下单 + 扣库存。** 库存服务返回超时，订单服务以为失败并回滚，但库存其实已经扣了，
超时只是响应丢了。

**场景三：写库 + 发消息。** 本地事务提交后调用 `rocketMQTemplate.send()`，消息发送失败，
下游永远收不到"订单已创建"，积分、物流、推荐全部不动。

**场景四：跨企业调用。** 本系统已经记账，调用合作方接口失败，对方系统没有对应流水，
两边账对不上。

这四个场景分别对应本书后面讲的三类解法：协调者统一提交（2PC/XA/AT）、业务补偿（TCC/SAGA）、
可靠消息 + 最终一致（本地消息表/事务消息）。

## 1.3 分布式事务的本质

很多资料把分布式事务描述成"让分布式系统也具备 ACID"，这是误解。

分布式事务真正要解决的问题是：**在部分失败不可避免的前提下，如何让多个数据副本在可接受的时间内
收敛到同一个业务事实**。它不是一个"是/否"的问题，而是一致性强度、可用性、成本之间的连续权衡。

工程上有三个层次的答案：

1. **避免**：能不能不做分布式事务？合并服务边界、同库同事务、用状态机把一个长流程拆成可重入的
   单库操作。成本最低，收益最高。
2. **刚性**：必须强一致且事务很短时，用 2PC/XA，或用 Seata AT 把两阶段做轻。
3. **柔性**：绝大多数互联网业务，用 TCC/SAGA/可靠消息做到最终一致，再配一套对账兜底。

**一个经验判断：如果一笔业务允许"几秒后一致"并且有对账手段，就不要用强一致方案。**

# 第 2 章 理论基础

## 2.1 ACID 在分布式下为何失效

| 特性 | 单库如何保证 | 分布式下为什么失效 |
|---|---|---|
| 原子性 A | 事务日志 undo | 多个资源管理器各自提交，没有统一的 undo |
| 一致性 C | 约束 + 事务 | 约束分散在多个库，跨库约束无法表达 |
| 隔离性 I | 锁 / MVCC | 不同库的锁互不可见，跨库读写没有统一快照 |
| 持久性 D | redo log + 刷盘 | 单库仍成立，但"整体持久"取决于最慢的那个 |

关键点在于：**隔离性和原子性都是"单资源管理器"内的概念**。一旦跨越 RM 边界，就必须有一个
外部协调者，而协调者本身也会失败。

## 2.2 CAP：P 是必选项

CAP 说一致性（C）、可用性（A）、分区容错性（P）最多同时满足两个。分布式系统里网络分区
不是"是否发生"而是"何时发生"，所以 P 必须选，真正的选择是 **C 还是 A**。

- 选 CP：分区期间拒绝服务，保证读到的一定是最新值。金融核心账务、库存扣减。
- 选 AP：分区期间继续服务，允许读到旧值，事后收敛。大多数交易、内容、社交业务。

BASE 就是 AP 方向的工程化表述：

- **Basically Available**：允许降级（限流、排队、返回旧值）
- **Soft state**：允许中间状态存在
- **Eventually consistent**：没有障碍后最终一致

## 2.3 刚性事务与柔性事务

| 维度 | 刚性事务 | 柔性事务 |
|---|---|---|
| 一致性 | 强一致（提交即一致） | 最终一致（中间态可见） |
| 隔离性 | 数据库保证 | 业务自己保证 |
| 典型方案 | 2PC、XA、Seata AT | TCC、SAGA、可靠消息 |
| 性能 | 差（锁 + 同步阻塞） | 好（异步、无长事务锁） |
| 侵入性 | 低 | 中到高 |
| 失败处理 | 协调者回滚 | 重试 + 补偿 + 对账 |
| 适用 | 短事务、强一致、低并发 | 长流程、高并发、可补偿 |

## 2.4 一致性光谱

把"一致性"当成一个连续变量更接近工程现实：

1. **强一致**：任何时刻读到的都是已提交的最新值（XA、单库）。
2. **准强一致**：提交后短暂窗口内可能读到旧值，但不会读到"部分成功"（Seata AT + 全局锁）。
3. **最终一致**：允许中间态，保证在有限时间内收敛（TCC、SAGA、消息）。
4. **尽力而为**：只保证"努力通知"，不一致靠人工（最大努力通知）。

选择哪一档，取决于**不一致的业务代价**：钱算错是事故，积分晚到十秒不是。
